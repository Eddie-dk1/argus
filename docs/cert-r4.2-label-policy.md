## Источник и смысл задачи

Используем только r4.2 из `insiders.csv` и соответствующие detail files.
Bundled answers/readme.txt называет insiders.csv master file of true positives,
а detail files — incident observables. Observables могут включать подготовку,
сопутствующие действия и использование чужого аккаунта. Поэтому основной target
называется **принадлежность официальным наблюдениям инцидента**, а не доказанная
вредоносность каждого отдельного действия. Это ограничение относится и к F1.

Издательские источники на принятом SSD snapshot:
`raw/answers/answers/{readme.txt,scenarios.txt,insiders.csv}` и
`raw/r4.2/r4.2/readme.txt`. Проверка полных строк описана в
[технической приёмке](cert-r4.2-acceptance.md).

## Метка события

1. Ключ события внутри snapshot — `(source, id)`. Между источниками одинаковые
   id допустимы; версия snapshot обязательна в будущих сохранённых артефактах.
2. `label=1`, если полная строка события совпадает с официальным observable
   соответствующего источника, включая account, timestamp и остальные поля.
3. Совпадение ключа при несовпадении строки — ошибка, а не отрицательная метка.
4. `label=0` для остальных корректных событий принятого snapshot: **не указано
   в observables**, а не независимо подтверждённое безопасное поведение.
5. Не распространяем положительную метку на все события участника, весь
   интервал start/end, весь PC, адресатов письма или соседние события.
6. Повторное упоминание одного события не увеличивает его вес. Все связи с
   инцидентами сохраняются. Конфликтующие строки одного ключа отклоняются.
7. Отсутствующие/неоднозначные detail files, неизвестные аккаунты, источники,
   неверные даты/ширины строк и выход observables за интервал — ошибка.

Без полной сверки observables с raw нельзя объявлять набор готовым к обучению.
Нулевые метки назначаются только после проверки полноты answer index. Новый
snapshot требует повторной приёмки; текущий индекс не является проверкой raw.

## Учётная запись и участник инцидента

`account_id` — поле `user` исходной строки; `incident_user` — пользователь из
master key. Их нельзя подменять друг другом. `incident_id` — имя detail file
внутри версии набора; scenario и границы инцидента сохраняются как provenance.
Несколько атрибуций одного события хранятся отдельными связями.

Сценарий №3 описывает кражу учётных данных руководителя и действия через его
аккаунт. Найдены 50 observables с отличающимся account: 20 logon и 30 email,
10 пар incident_user/account. Эти записи сохраняют label=1 по правилу
observable membership и относятся к дню **аккаунта из журнала**. Это не
утверждение, что владелец скомпрометированного аккаунта является злоумышленником.

## Метка пользовательского дня

- Единица анализа: `(snapshot_id, account_id, calendar_date)`.
- День — дата исходного timestamp без назначения часового пояса Москвы/UTC:
  timestamps издателя здесь трактуются как naive local calendar time.
- В первую популяцию входят только account-days хотя бы с одним событием из
  пяти журналов. Дни отсутствия активности не создаём и не считаем нормальными.
- `day_label=1`, если хотя бы одно событие этого аккаунта в этот день имеет
  label=1; иначе 0 с той же оговоркой о benchmark background.
- Агрегируются **все** события дня, а не только observables. Сохраняется
  day→source events mapping и отдельно positive-event evidence.
- Прогноз по полному дню доступен после его окончания. Он не является
  ранним предупреждением или прогнозом следующего дня.
- Интервалы master key сами по себе не создают положительные дни.

Функция `positive_days()` возвращает только положительный индекс. Полная
популяция, отрицательные дни и prevalence появятся при raw→user-day preparation.
Их нельзя вывести из одних answer files.

## Разделение данных: CERT protocol amendment 1.1

Уточнение первичного no-user-overlap split, без изменения synthetic reference:

1. Узлы — все 1000 аккаунтов принятой популяции.
2. Для каждого инцидента соединяем incident_user со всеми account из его
   observables. Не соединяем аккаунты по обычной переписке, PC или отделу.
3. Транзитивно связанные аккаунты составляют неделимую группу. Изолированные
   аккаунты составляют одноэлементные группы.
4. Все raw events, user-days и окна каждого аккаунта остаются внутри одной
   части данных; связанный инцидент не пересекает train/validation/test.
5. Цель распределения — приблизительно 60/20/20 пользователей, seed 42.
   Учитывать normal/positive account support и сценарии 1/2/3 на уровне групп.
   Точные пропорции не обещаются из-за неделимости групп. Алгоритм распределения
   и полный assignment manifest фиксируются в следующем этапе **до обучения**.
6. Проверять отсутствие пересечения accounts, groups, incident IDs и event IDs;
   сохранять group sizes, account/day support и scenarios по каждой части.
   Нельзя перераспределять группы по результатам модели.

Answer metadata допустимы для target и организации split, но не для признаков.
Идентификатор группы — только provenance; его нельзя подавать модели.
Для held-out аккаунтов используются train-fitted global/peer fallbacks и
cold-start indicators. Подгонка персональных профилей по их полным историям
запрещена. Temporal-with-user-overlap остаётся отдельным экспериментом.

## Реализация и воспроизведение

[cert_labels.py](../src/datasets/cert_labels.py) строит индекс полных строк,
атрибуций, положительных дней и связанных аккаунтов. Он не меняет raw, не
строит признаки, не распределяет группы и не обучает модели.

```bash
python3 src/inspect_cert_labels.py \
  --answers "$ARGUS_DATA_ROOT/cert_r4_2/raw/answers/answers" \
  --psychometric "$ARGUS_DATA_ROOT/cert_r4_2/raw/r4.2/r4.2/psychometric.csv"
PYTHONPATH=src python3 -m unittest discover -s tests -v
```

CLI печатает сводку и SHA-256 прочитанных answer files. При будущей preparation
сохранить также hash policy config, raw manifest, account population и code
revision. Record-level labels/mapping остаются вне Git рядом с dataset artifacts.
Публикуемый отчёт содержит только агрегаты; вопрос лицензии raw остаётся открытым.

Изменение membership, day boundary, отрицательного класса или split grouping
требует новой версии policy до нового финального эксперимента. Текущая policy
не определяет новые истинные метки для what-if копий событий.

## Распределение групп — реализация 13 ноября 2026

Добавлен [cert_group_greedy_v1](../src/datasets/cert_split.py). Группы
обрабатываются по редкости сценария, размеру, числу положительных дней;
SHA-256 от seed и идентификатора разрешает равенства независимо от порядка
входных строк. Жадный алгоритм минимизирует прирост суммы квадратов отклонений
от 60/20/20, нормированных на общий размер каждого показателя: аккаунты,
положительные аккаунты, положительные дни и число инцидентов каждого сценария.
Это эвристика, не гарантия глобального оптимума или точных пропорций.

При наличии трёх и более групп резервируется поддержка сценария во всех частях.
При двух группах обязательны train и test, validation остаётся без этого сценария.
При менее двух группах или если эвристика не может сохранить поддержку, команда завершится
ошибкой, а не разделит группу. Новое распределение по метрикам модели запрещено.

```bash
python3 src/prepare_cert_split.py \
  --answers "$ARGUS_DATA_ROOT/cert_r4_2/raw/answers/answers" \
  --psychometric "$ARGUS_DATA_ROOT/cert_r4_2/raw/r4.2/r4.2/psychometric.csv" \
  --output "$ARGUS_DATA_ROOT/cert_r4_2/manifests/account_split_v1.json"
```

Каталог назначения должен существовать. Существующий manifest не перезаписывается.
Сохраняются account→group→split, incident→split, сводка поддержки, seed,
версии policy/алгоритма и SHA-256 answers, популяции, конфигурации и исходного кода.
Manifest с идентификаторами остаётся локальным артефактом вне Git.
Все account-days и события при следующей подготовке должны наследовать это
назначение; неизвестный аккаунт — ошибка. Нормальные дни, полная prevalence
и соответствие raw event IDs ещё требуют отдельной проверки при подготовке.
