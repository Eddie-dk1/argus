# CERT r4.2: подготовка активных дней аккаунтов

Пункт 2 подготовки CERT, 13 ноября 2026. Версия признаков:
`cert_account_day_raw_v1`. Это агрегаты исходных значений, до обучения,
масштабирования, исторических профилей и формирования окон.

## Контракт

- Единица — активный `(snapshot_id, account_id, calendar_date)`.
  Неактивные дни не добавляются. Calendar date берётся из timestamp издателя
  без назначения часового пояса; полный день доступен после его окончания.
- Snapshot ID — SHA-256 канонического JSON с SHA-256 пяти журналов и
  `psychometric.csv`. Последний используется только как реестр аккаунтов;
  психометрические оценки не становятся признаками.
- Метка дня — максимум точных observable membership labels его событий.
  Полные строки официальных наблюдений должны совпасть с raw, включая content.
  Background означает отсутствие в официальных observables, не доказанную норму.
- Account, group и split наследуются из замороженного `account_split_v1.json`.
  Его назначения воспроизводятся и сверяются с текущими answers и популяцией.
  Метки, сценарии, идентификаторы и служебные связи не входят в `feature_columns`.
- Источники читаются с проверкой хронологии и сливаются по дате, секунде,
  порядку `logon/device/file/http/email`, порядковому номеру CSV record.
  При равных timestamps используется этот детерминированный порядок.
  Нарушение порядка приводит к ошибке, а не незаметной перестановке.
- В памяти находится один календарный день. Уникальность ID проверяется
  внешней сортировкой отдельно для каждого источника. Одинаковые ID между
  источниками допустимы. Нужны свободные 10 GiB и команда `sort`, используемая
  также существующим CERT audit (`-S`, `--parallel`, `-T`).

## Признаки v1 и формулы

Все значения числовые, конечные и неотрицательные. Счётчики, секунды,
байты и бинарные индикаторы целочисленные; доли, средние и стандартное
отклонение вещественные. Никакого fitting на train/validation/test здесь нет.
Полный порядок колонок зафиксирован в `contract.json` и `cert_days.FEATURES`.

| Группа | Определение |
|---|---|
| Объём источников | Число событий каждого источника, total, число активных источников; доля источника = count / total |
| Время | Первая/последняя секунда от полуночи, разность last−first; суббота/воскресенье отдельным флагом |
| Off-hours | Секунда < 07:00 либо ≥ 19:00; общий и отдельные счётчики по источникам. Это фиксированная эвристика, не персональный график и не метка аномалии |
| Интервалы | Между всеми соседними событиями аккаунта внутри дня: count, mean, population std, max. Равные timestamps дают нулевой интервал; для одного события все четыре значения 0 |
| PC | Число уникальных PC внутри дня, общее и по источникам; исходные PC не кодируются как числа |
| Logon | Число Logon и Logoff; иные action отклоняются |
| Device | Connect/Disconnect, число пар, сумма секунд в однозначно найденных парах одного account/PC внутри дня; непарные события считаются отдельно |
| File | Число копирований на съёмный носитель (такова семантика каждой строки r4.2); уникальные filename; счётчики групп расширений |
| HTTP | Запросы; уникальные исходные URL и нормализованные lowercase hostnames из http/https; число URL без распознаваемого hostname |
| Email | Число сообщений; сумма/максимум/среднее size в байтах без вложений; сумма числа вложений и число сообщений с вложениями |
| Получатели | to+cc+bcc: trim, lowercase, дедупликация внутри сообщения. Суммы внутренних/внешних получателей по сообщениям, уникальные адресаты дня, число сообщений с внешним адресатом. Internal — домен ровно `dtaa.com` |

Device: повторный Connect при открытой паре считает предыдущий Connect
непарным и начинает новую пару. Disconnect без Connect считается непарным.
Оставшиеся Connect в конце дня считаются непарными. Пары через полночь
не восстанавливаются, их длительность не выдумывается. Суммы длительностей
могут включать параллельные PC и не равны длительности присутствия человека.

Группы расширений (регистр игнорируется): document = doc/docx/xls/xlsx/ppt/pptx/
txt/rtf/odt; pdf; archive = zip/rar/7z/gz/tar; image = jpg/jpeg/png/gif/bmp/tif/tiff;
executable = exe/dll/bat/cmd/ps1/sh; всё остальное = other.
Filename diversity сохраняет точные строки издателя.

Нет событий источника за день → нули в его счётчиках, разнообразии,
размерах, долях и длительностях. Источник целиком отсутствует → ошибка,
не нулевой источник. В r4.2 нет полей HTTP upload/download, file bytes,
failed logon или надёжного receive action для email: они не изобретаются.
Email привязывается к logged account, не к адресатам.
Организационные и психометрические показатели не используются.

## Выходной каталог

Каждый запуск создаёт новый `cert_days_<uuid>` внутри существующего output root.
Raw и предыдущие запуски не изменяются.

| Файл | Назначение |
|---|---|
| `account_days.csv` | Числовые агрегаты, label и явно отдельные provenance-колонки; порядок date/account |
| `<source>_membership.csv.gz` | Все события этого источника: day_key, event_id, raw_record_index, second, label |
| `positive_evidence.jsonl` | Только совпавшие observables с incident/user/scenario attribution для расследования, вне model inputs |
| `day_context.jsonl.gz` | Отсортированные уникальные PC, domains и recipients дня для будущего расчёта истории; служебные данные, не готовые признаки новизны |
| `contract.json` | Snapshot ID, версия, allowlist признаков, правила ID/порядка/пропусков, границы текущей реализации |
| `quality_report.json` | Популяция, prevalence, число событий/положительных дней, проверки по split и источнику |
| `account_split.json`, `raw_manifest.json`, `acceptance_audit.json`, `label_policy.json` | Копии входных контрактов |
| `provenance.json` | SHA-256 входных контрактов, answers и исполняемого исходного кода; версия Python/platform |
| `status.json`, `complete.json` | Состояние и контрольные суммы всех готовых файлов |

`day_key = account_id:YYYY-MM-DD` имеет смысл внутри snapshot из contract.
Полный item_id включает snapshot. Ключ события — `(snapshot_id, source, event_id)`.
`raw_record_index` начинается с 1 после заголовка, это номер CSV-записи,
**не физической строки**: quoted content может содержать переводы строк.
Связь с raw восстанавливается по файлу источника и номеру записи с проверкой ID
и SHA-256 исходного файла. Текст content не копируется в признаки.

Полная проверка успешности: SHA-256 каждого исходного журнала, число строк
по audit, все точные observables, равенство множества положительных дней,
уникальность source-qualified ID и конечность агрегатов. Только затем пишется
`complete.json` с SHA-256 всех файлов. Незавершённые каталоги не являются
готовой подготовкой; после аварийного завершения status может остаться running.
Автоматическое возобновление не реализовано. Контрольные суммы обнаруживают
изменения, но не являются криптографической подписью доверенного издателя.

## Воспроизведение

`ARGUS_DATA_ROOT` — существующий корень данных на SSD, содержащий `cert_r4_2`.

```bash
python3 src/prepare_cert_days.py \
  --source-dir "$ARGUS_DATA_ROOT/cert_r4_2/raw/r4.2/r4.2" \
  --answers "$ARGUS_DATA_ROOT/cert_r4_2/raw/answers/answers" \
  --split "$ARGUS_DATA_ROOT/cert_r4_2/manifests/account_split_v1.json" \
  --raw-manifest "$ARGUS_DATA_ROOT/cert_r4_2/manifests/raw_file_manifest.json" \
  --audit "$ARGUS_DATA_ROOT/cert_r4_2/manifests/cert_acceptance_audit.json" \
  --output-root "$ARGUS_DATA_ROOT/cert_r4_2/processed"

PYTHONPATH=src python3 -m unittest discover -s tests -v
```

Raw-derived artifacts с идентификаторами остаются на SSD, вне Git. В репозитории
хранятся только код, тесты, контракты и агрегированное описание результатов.

Следующий пункт: train-fitted преобразования, история строго из доступного
прошлого, cold-start policy для held-out аккаунтов, окна и подключение к

новизны, модели, выбора порога или оценки качества детекторов.
Ограничение сценария 3 сохраняется: нет validation support, test содержит
только одну независимую группу этого сценария.
