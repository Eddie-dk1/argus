# CERT r4.2: пункт 4 — финальная оценка

Протокол `cert_r4_2_frozen_final_v1` зафиксирован 13 ноября 2026 года до
первого model scoring на реальном test. [Конфигурация](../configs/cert_r4_2_final_v1.json)
связывает по SHA-256 series manifest пункта 3, frozen registry и дневную
подготовку. [Принцип владельца проекта](../CONTRIBUTING.md#before-changing-an-experiment)
закреплён в правилах: улучшение метрик не оправдывает утечки, подмену target,
split, популяции или выбор удачного seed.

## Граница финального эксперимента

- Оцениваются все **30** frozen кандидатов: две policy × RF/IF/LSTM × seeds
  7, 21, 42, 84, 168. Ничего не обучается и не выбирается заново.
- Ожидаемая общая популяция — **65 433 test endpoint-дня**, 160 positive и
  65 273 background, после исключения первых четырёх дней каждого аккаунта.
  Target — official observable membership последнего дня пятидневного окна.
- Порог, epoch, scaler, feature builder, vocabulary и checkpoint закреплены
  до test. Новая оценка не меняет train/validation, исходные labels или split.
- Публикуются все seed, mean/sample std/min/max, validation→test различия,
  PR-AUC, precision/recall/FPR/confusion и per-scenario recall/FN.
- Сценарные атрибуции читаются только для отчёта после inference. Повторы
  attribution не увеличивают число дней; день с несколькими сценариями может
  входить в несколько отдельных denominators. Число независимых групп явно
  сообщается. Сценарий 3 имеет только одну test-группу.
- CPU, один поток; inference после одного прогрева и пять повторов на готовой
  полной матрице. LSTM batch 128, tabular batch — весь cohort. Время загрузки
  модели и построения готовых окон хранится отдельно. Это не raw→alert latency.

## Проверки перед доступом к test

Все config/model/state/preparation hashes и thresholds сверяются с frozen
registry; проверяется полный набор policy/model/seed без пропусков/дубликатов.
Core inference source сравнивается с snapshot пункта 3: feature/utility/LSTM
files по хешу, `inputs`/`score` по AST. Версии numpy/pandas/sklearn/torch также
должны совпасть. Новый отчёт и timing не меняют model input или score function.

Во время final заблокированы вызовы RF/IF fit, optimizer, feature fitting и
threshold selection. Сохраняются точные NPZ scores/decisions с исходным dtype,
CSV как читаемое представление, numerical X и ordered window membership.
Сравнение разных preparation разрешается явно и всё равно требует совпадения
snapshot, target, каждого item ID и label. Переименование preparation не может
скрыть изменение оценочных дней или target.

Начало финальной фазы и первое открытие prepared test фиксируются в
`test_exposure.json`. После этого текущий test — использованный набор;
следующие модели не получают статуса независимо подтверждённых на нём.
Для новых confirmatory claims нужен новый независимый holdout. Development
group-CV остаётся допустимым способом исследования новых гипотез.

## Воспроизведение

`ARTIFACT_ROOT`, `FROZEN_SERIES`, `CERT_DAYS` — существующие каталоги на SSD.
Каждый final создаёт новый UUID-каталог; повторный запуск проверяет
воспроизводимость и не делает test снова нетронутым.

```bash
OMP_NUM_THREADS=1 OPENBLAS_NUM_THREADS=1 MKL_NUM_THREADS=1 VECLIB_MAXIMUM_THREADS=1 \
python3 src/run_cert_final.py --root "$ARTIFACT_ROOT" \
  --series "$FROZEN_SERIES" --days "$CERT_DAYS" \
  --plan configs/cert_r4_2_final_v1.json
```

### Диагноз и необходимые изменения

**Текущие модели недостаточно качественны для практической детекции.** RF
остаётся наиболее сильным baseline, но низкий recall — серьёзная проблема.
Большой validation→test разрыв v1 RF совместим с ранее обнаруженным сдвигом
доступности истории и различиями групп; сам по себе он не доказывает единственную
причину или конкретную форму переобучения. Core inference/weights/config
подтверждены; ошибки не исправлялись подстановкой новых порогов на test.

Publisher `raw/answers/answers/scenarios.txt` описывает сценарий 2 через рост
использования съёмного носителя относительно прежней активности пользователя.
В текущих 71 признаке есть абсолютные device/file counts, но personal robust
history относится к **total_events**, а global-only полностью отключает её.
Персональных rolling baselines для file/device в этой версии нет. Поэтому
приоритетная гипотеза — одинаковая для train/held-out причинная история плюс
отдельный контролируемый эксперимент с generic source-specific изменениями
USB/file activity относительно доступного прошлого. Это не доказательство,
что новые признаки решат задачу: observable days могут включать подготовку,
а не только само копирование данных.

[Следующий план улучшений](cert-r4.2-improvement-plan.md) задаёт небольшие
пакеты: причинная история без будущего/меток, group-CV также для RF/IF,
отдельная проверка endpoint-specific reconstruction score. Dropout, weight
decay или увеличение сети сами по себе не обоснованы текущими результатами.
Новые модели оцениваются на development; подтверждение требует независимого
holdout. Старый test после этого final допускает только явно exploratory
сравнение новых вариантов. Порог/labels/split этой серии остаются прежними.

### Проверки и границы завершения

Полный final прошёл без технических сбоев. Все 30 evaluation artifacts имеют
`complete.json`; весь итоговый manifest независимо проверен. Все 30 исходных
model/checkpoint hashes и candidate manifests после final совпали с freeze.
Сверены exact scores/decisions, finite X, ordered membership endpoints,
идентичность популяции/target и пересчитанные metrics. Все **49 тестов прошли**,
включая запрет fit/threshold selection, cross-preparation guard, дубликаты
атрибуций и end-to-end final на искусственном наборе.

Все четыре пункта первой CERT-серии завершены. Это не означает выпуск v0.3.0,
готовую production-систему или подтверждение будущих улучшений на новом test.
