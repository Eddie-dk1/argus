Это отчёт исходного пункта 2. Продолжение уже выполнено:
[пункт 3 — global-only контроль, фактическая group-CV и пять seed](cert-r4.2-robustness.md).

[План серии](cert-r4.2-benchmark.md) и config не изменены; seed 42,

## Переобучение, недообучение и сдвиг входов

MSE в таблице измерена в eval-режиме на конце каждой эпохи. Train — все окна
fit; validation — 63 968 окон, все дни которых background, без примеси окон с
положительным внутренним днём. Это диагностические когорты, а не новая цель
основной оценки по endpoint.

| Эпоха | Train MSE | Validation all-background MSE | Validation F1 | Validation PR-AUC |
|---|---:|---:|---:|---:|
| 1 | 0,329932 | 8,262990 | 0,008174 | 0,006389 |
| 2 | 0,269394 | 8,434031 | 0,006472 | 0,004539 |
| 3 | 0,247369 | 8,377960 | 0,006055 | 0,003814 |
| 4 | 0,233405 | 8,495678 | 0,006358 | 0,003772 |

| 6 | 0,211288 | 8,732039 | 0,007073 | 0,002833 |

Train reconstruction улучшается, а перенос на held-out аккаунты ухудшается.
Дополнительные эпохи в этом запуске не помогли. Но разрыв нельзя приписать
только запоминанию train: уже на первой эпохе validation MSE примерно в 25 раз
больше, и измерен сильный сдвиг доступности истории.

На выбранном checkpoint доля суммарной squared reconstruction error фоновых
validation-окон (сумма по всем окнам, позициям и признакам):

| Признак | Доля ошибки |
|---|---:|
| cold_start | 54,98% |
| prior30_days_log1p | 12,69% |
| history_missing | 8,94% |
| prior30_events_log1p | 6,20% |
| prior7_events_log1p | 4,72% |
| Эти пять вместе | **87,53%** |

У background train cold_start=1 примерно в 0,30% дней, history_missing=1 в
1,51%; у validation оба равны 1 во все дни. Исторические суммы в held-out
равны нулю по frozen policy, а у train почти всегда ненулевые. После train-only
стандартизации редкий train-флаг cold_start становится большим отклонением для
каждого held-out аккаунта. Автоэнкодер в большой мере измеряет различие условий
подготовки, а не отделяет observables от background.

Это прямое измерение распределений и residuals. Вывод, что изменение политики
истории улучшит детекцию, **пока гипотеза**, требующая отдельного эксперимента.
Малый F1 не доказывает недообучение, необходимость большей сети или недостаток
эпох. Ранняя остановка сработала; продление текущего обучения не обосновано.

## Кросс-валидация: что проверено и нужна ли она

**Обучающей cross-validation в текущем runner нет.** Используются один frozen
group split и validation; пять model seeds из пункта 3 не являются CV.
Для первого фиксированного baseline такое разделение допустимо. При сравнении
вариантов истории, регуляризации и параметров одной validation недостаточно
для устойчивого выбора: перед широким подбором нужна внутренняя group-CV.

Проверена только техническая возможность `StratifiedGroupKFold(3, shuffle=True,
random_state=42)` внутри frozen train, по incident-connected group, не по
случайным дням/окнам. Аккаунты и группы между сторонами каждого fold не
пересекаются; обе метки присутствуют:

| Fold | Fit days / positive | Validation days / positive |
|---|---:|---:|
| 1 | 132 800 / 444 | 66 365 / 202 |
| 2 | 132 768 / 424 | 66 397 / 222 |
| 3 | 132 762 / 424 | 66 403 / 222 |

Это **проверка разбиения**, не обучение CV и не новые CV-метрики; размеры выше
относятся к дням до исключения warmup окон. Полный CV pipeline пока не
реализован. Нельзя просто подать существующие standardized CSV в cross_val_score:
их scaler/global vocab уже fitted по всему исходному train, включая будущие
inner validation folds. Для каждого fold надо заново fit state только на
fold-train, пересчитать историю/fallback, окна и threshold calibration.
Внутри fit-fold потребуются свои данные для ранней остановки/порога, если
оценочный fold должен оставаться независимым от их выбора.

Группировка и fitting преобразований внутри каждого fold следуют
[правилам group-CV sklearn](https://scikit-learn.org/stable/modules/cross_validation.html#cross-validation-iterators-for-grouped-data)
и [защиты от preprocessing leakage](https://scikit-learn.org/stable/common_pitfalls.html#data-leakage).
В train только одна независимая группа сценария 3: обеспечить этот сценарий
по обе стороны всех inner folds невозможно. CV этого ограничения не устраняет.

## Dropout, регуляризация и приоритет улучшений

1. **Первым проверить согласованную политику истории.** Минимальный контроль —
   отдельный именованный global-only вариант с одинаковой доступностью истории
   у train и held-out, без использования будущих событий новых аккаунтов.
   Сравнить его с текущим на development data, сохранив основной benchmark.
   Следующий возможный вариант causal-online потребует отдельного контракта;
   не надо добавлять оба варианта сразу. Изменение policy создаёт новую подготовку,
   а не переписывает эту серию и её результаты.
2. **Dropout сейчас не добавлять.** Нет подтверждения, что он устранит главный
   измеренный сдвиг. В encoder/decoder по одному recurrent layer; встроенный
   `nn.LSTM(dropout=...)` действует между stacked layers и здесь сам по себе не
   создаст нужной регуляризации. Это следует из
   [документации PyTorch](https://docs.pytorch.org/docs/2.12/generated/torch.nn.LSTM.html).
   Явный dropout в другой точке — уже проверяемое изменение архитектуры.
3. **Weight decay / AdamW пока не включать.** Сейчас Adam с weight_decay=0;
   ранняя остановка и ограниченный latent size уже ограничивают обучение.
   Проверить небольшой заранее заданный weight decay имеет смысл, если после
   согласования истории сохраняется разрыв качества на корректных group-folds.
   Объявлять улучшение до сравнения нельзя. Значение по умолчанию подтверждено
   [PyTorch Adam](https://docs.pytorch.org/docs/2.12/generated/torch.optim.Adam.html).
4. **Не увеличивать сеть/эпохи и не делать oversampling/SMOTE без гипотезы.**
   Здесь reconstruction fit не использует положительные окна; балансировка
   классов не решает измеренную проблему доступности истории. Полезность любого
   изменения оценивать по F1, precision/recall, PR-AUC и количеству FP при
   одинаковой популяции, а не по accuracy или одному ROC-AUC.

Моя оценка: технический путь воспроизводим и проверяем, но качество текущей
LSTM недостаточно для практической детекции. Приоритет — согласование входов,
затем устойчивость/корректная group-CV, а не добавление механизмов регуляризации
ради наличия. Формально следующий пункт фиксированной серии — пять seeds;
перед масштабированием серии стоит отдельно проверить выявленную проблему.
Ни пять seeds, ни CV не заменяют ещё не открытый final test.

## Проверки утечек и артефакты

Серия: `processed/cert_benchmark_step2_55ebdd6e4ab0488ebcd36bd905e64199` на SSD.
Кандидат: `candidate_5b1eeaa920ce4cb4991ee66ae327bbb5` внутри серии.
Сохранены исходники, frozen plan/config, weights, numerical inputs, history,
residuals, распределения истории, scores, thresholds, timing и checksums.

Повтор кандидата на существующем SSD root (всегда создаёт новый UUID-каталог):

```bash
OMP_NUM_THREADS=1 OPENBLAS_NUM_THREADS=1 MKL_NUM_THREADS=1 VECLIB_MAXIMUM_THREADS=1 \
python3 src/experiment.py --root "$ARTIFACT_ROOT" candidate \
  --preparation "$CERT_PREPARATION" --model lstm_autoencoder \
  --config configs/cert_r4_2_experiment_v1.json --diagnostics
```

- Проверены binding preparation/config hashes, frozen feature state, отсутствие
  train/validation account overlap, exact endpoint IDs/labels и полный ordered
  membership окон. Численные X независимо восстановлены из parent CSV.
- Все fit-окна имеют пять background дней; все допустимые окна присутствуют.
  Label, IDs, group и scenario не являются входными feature columns.
- После reload scores совпали с rtol=1e-6, atol=1e-7; решения совпали точно.
  Выбор эпохи, метрики, общая RF/IF/LSTM популяция и SHA-256 сверены.
- Open guard запрещал любые чтения `test.csv`, включая хеширование; попыток
  не было. Тесты подтверждают train-only fitting и причинность истории при
  frozen global state, отказ при group leakage и работу без test-файла.
- Диагностика сохраняет RNG через fork_rng. Новый трёхэпоховый тест с/без
  диагностики даёт побитово одинаковые веса, предсказания и выбранную эпоху.
  Все **42 теста проекта прошли**. Проверены синтаксис Python/shell, локальные
  ссылки, совпадение config hash с планом и `git diff --check`.

По проверенным путям утечек между split не обнаружено. Это offline
account-holdout: global state fitted на всех train-днях, календарные периоды
разных аккаунтов могут совпадать. Это не проверка прогноза будущего периода
по одному прошлому временному отрезку. Background не доказанная безопасность;
validation содержит только 12 positive аккаунтов, а не 180 независимых
инцидентов. Сценарий 3 на validation не оценивается. Эти ограничения остаются.
